# Security

Synced: 2026-10-09

Sealwax handles hostile content (every incoming message), long-lived credentials and private data. This page is the threat model and the rules every change must keep. M9 reviewed it rule by rule against the code as built through M8, with fuzzing and an advisory check (ML-093, [review](#review-and-fuzzing-m9)), and built three of the review's proposals ([hardening](#hardening-m9)).

## Threat model

| Threat | Example | Defence |
| --- | --- | --- |
| Hostile HTML | Scripts, tracking pixels, CSS `url()` beacons, `@import`, meta refresh, forms, iframes, SVG scripts, `<a ping>`, DNS prefetch, `<base>` tricks | Layered WebKit hardening ([below](#message-rendering)); the hostile-HTML suite in CI (ML-065) |
| Tracking | Remote images reveal when and where a message was opened | Nothing remote loads until allowed per message (for the session) or per sender (a list the user keeps); a forged From address can borrow a listed sender's permission, still https only and without cookies |
| Phishing | Link text shows one domain, the target is another | Real URL on hover; mismatch warning; links open in the browser, never in the app |
| Dangerous attachments | `.desktop`, `.sh`, `.AppImage`, `.jar` launched by a double-click; names that hide their type | Never opened directly; warning and Save only; safe names, and the check reads the name a file is opened under too; content checked at Open |
| `mailto:` abuse | `attach=` parameters that pull local files into a message | `attach` / `attachment` parameters ignored; nothing is sent without the user |
| Network attackers | TLS stripping, STARTTLS downgrade and response injection, forged certificates | TLS everywhere, STARTTLS required when used and nothing sent ahead of the handshake read as if it came over TLS, platform certificate verification, plaintext authentication refused |
| Credential theft | Passwords or tokens in files, logs or crash output | Secrets only in the Secret Service; grep tests over config, database and logs |
| Metadata leaks | Hostname in Message-ID, EHLO and Received headers; Bcc recipients revealed | Neutral `hello_name`; Message-ID with the sender's domain; no Bcc header in the transmitted copy |
| Privacy of setup | The address sent to third parties during autodetect | Full address only to the domain's own HTTPS autoconfig, never in a redirect or a Referer; the ISPDB gets only the domain |
| Malformed mail | Parser crashes or hangs on hostile MIME | mail-parser, with a panic beneath `message::parse` caught; the reader's and the composer's parsing on worker threads; at most 256 KiB of a message's HTML parsed into a tree outside the reader; an account's sync started again after a panic beneath it; coverage-guided fuzzing of message parsing, HTML handling, autoconfig XML and Sealwax's own parsers ([M9](#hardening-m9)) |
| Hostile or broken rules | A Sieve script pasted from elsewhere that redirects, replies, deletes for good or makes the run slow | Sealwax's subset has no command that sends mail or expunges; `discard` moves to Trash and `\Deleted` can't be set; at most 1 MiB and 32 levels of nesting, each command run at most once per message, `:matches` in at most value × pattern steps; a script outside the subset runs nothing ([mail rules](#mail-rules-m9)) |
| Data loss | Crashes while writing drafts or sending | WAL store; draft autosave; idempotent op replay; at-most-once send ([ADR-015](DECISIONS.md#adr-015--op-queue-optimistic-overlay-undo-at-most-once-send-2026-10-04)) |

## Rules

### Transport

- IMAP on 993 (implicit TLS) or 143 with STARTTLS required; SMTP on 465 (implicit TLS, preferred per RFC 8314) or 587 with STARTTLS required; POP3 on 995 or 110 with STLS required.
- If a server offers no TLS, the account is refused with an explanation; there is no plaintext mode.
- **STARTTLS response injection:** nothing a server (or a man in the middle) sends after the OK to STARTTLS or STLS is ever read as if it came over TLS. IMAP drops async-imap's buffer with the plaintext connection; POP3 refuses the account when anything is buffered; SMTP hands lettre, which keeps its read buffer across its TLS upgrade, a stream that passes on at most one line per read until the handshake and fails the handshake when anything is left over (M9: before, a man in the middle could answer for the server over TLS, and every later reply was read one behind). Bytes that arrive after the OK break the handshake.
- Certificates are verified with rustls and the platform verifier (the system trust store).
- **A pinned certificate, on this computer only** (issue #9, Proton Mail Bridge; [ADR-007 amendment](DECISIONS.md#adr-007-amendment--a-pinned-certificate-for-a-server-on-this-computer-2026-10-13)): a server whose host is `localhost`, an address in 127.0.0.0/8 or `::1` can be trusted with exactly one certificate, named by its SHA-256 in `accounts.toml`. The file refuses a pin on any other host, and the engine ignores one there. The connection must reach a loopback address. The certificate must have exactly that SHA-256, and the handshake's signature is still checked against its key; its name, dates and CA flag are not. For SMTP with STARTTLS, lettre checks the signature and Sealwax compares the certificate with the pin before anything but EHLO is sent. A certificate is pinned only after the user saw its fingerprint in the assistant and chose to trust it. Reading it for them sends no login, only CAPABILITY, STLS or `EHLO [127.0.0.1]` before STARTTLS, and stops the handshake at the certificate.
- Authentication prefers OAuth (XOAUTH2 / OAUTHBEARER) and AUTHENTICATE PLAIN over LOGIN.
- POP3 (M8): only the greeting and STLS cross in plaintext, and anything the server sends after STLS's `+OK` refuses the account (STARTTLS injection); CAPA is read over TLS only; USER and PASS go only over TLS; credentials with CR, LF or NUL are never sent. POP3 logs counts, sizes, timings and the mechanism, never UIDLs.

### Credentials

- Passwords and refresh tokens are stored only in the Secret Service keyring (oo7). Access tokens stay in memory.
- `config.toml`, `keys.toml`, `accounts.toml`, the database, the blob store and the logs never contain a secret: `engine/tests/no_secret_in_files.rs` adds accounts with a known dummy password and searches every file and trace-level log line for it.
- Removing an account deletes its `accounts.toml` entry, then its database rows, its blobs and its secrets, in that order; a removal that fails or crashes after the entry is gone is journalled and finished at the next start. An entry deleted by hand only detaches the account: its data and secret stay until it is removed in Sealwax.
- Without a keyring, secrets are kept in memory for the session and a banner says so (ML-048: the window's banner, until dismissed for the session). A keyring that opens but stays locked is an error, not the memory fallback.
- A password typed again is checked on the incoming server (IMAP or POP3) and on SMTP before it replaces the stored one; a refused one is never stored.
- **Development builds only** (`cfg!(debug_assertions)`; release builds never read them): `SEALWAX_TEST_CA=<file>` replaces the system's trust with exactly that CA (the mail testbed's), and `SEALWAX_SECRETS=memory` keeps secrets out of the keyring. Self-tests that start the real engine (`engine-start`) use both.

### Message rendering

Every layer stays even when another would suffice ([ADR-011](DECISIONS.md#adr-011--reading-pane-approach-a-with-hardened-webkit-2026-10-04) and its S2 and S7 amendments). S2 checked them against 47 hostile cases: 0 connections, 0 TLS hellos and 0 script traces at a local canary, while a no-defence control showed the attacks were live. M5's suite (ML-065) runs 60 cases in `tools/ci.sh --ui`, S2's 47 plus M5's surfaces and a conversation of hostile bodies, with a DNS canary that records and refuses every name the app or WebKit looks up: production passes show 0 connections, 0 requests, 0 TLS hellos, 0 DNS lookups and 0 script traces. M1's reader (ML-027) passed the same 47 cases in three runs: as shipped, with real pointer clicks, and in pooled views after Show images. Every run shows 0 connections, 0 requests, 0 TLS hellos and 0 script traces; after Show images the canary saw only TLS hellos.

1. `enable-javascript-markup = false`: no script in a message ever runs; WebKit also strips `javascript:` URLs and `srcdoc` attributes. It makes `<noscript>` content live, so the other layers must stay. Sealwax's own helper scripts run in an isolated world.
2. `default-content-security-policy` set when each view is built: `default-src 'none'; img-src cid: data: https:; style-src 'unsafe-inline'; font-src cid: data:; form-action 'none'; base-uri 'none'; frame-src 'none'; upgrade-insecure-requests` (so remote images the user allows load over TLS).
3. A WebKit content filter blocks every URL except `cid:`, `data:` and `about:` until the user allows remote content for that message or sender. A second filter, on in every view whatever the user allowed, blocks every load WebKit checks as a ping: `<a ping>`, `<link rel=dns-prefetch>` and `<link rel=preconnect>`, which no CSP governs.
4. Link clicks and form submits are intercepted in Sealwax's isolated world, because WebKit connects to a clicked link's host before `decide-policy` answers. Sealwax opens only absolute http(s) links with a host, and mailto links, after the link-mismatch check, in the default browser or mail handler (`gtk::UriLauncher`). Relative, `cid:`, `data:`, `file:` and `javascript:` targets are dropped, and a headless run never opens a link. `decide-policy` blocks every navigation as the backstop. A link whose visible text names another registrable domain than its target, or whose address puts a name before an `@` (`https://bank.example@evil.example/`), shows a warning on hover and asks before opening, with Cancel as the default; the real target shows in a strip on hover and focus, hosts that mix alphabets in punycode. Plain-text bodies link only http(s), `www.` and mailto targets (M5, ML-062).
5. An ephemeral network session (no cookies accepted, so allowed images can't link messages through a cookie; no cache on disk; TLS errors fail; downloads are cancelled). The runtime features `LinkDNSPrefetch`, `LinkPreconnect`, `LinkPrefetch`, `LinkPreload` and `SpeculationRulesPrefetch` are off where WebKit has them (`Settings::set_feature_enabled`; a unit test checks that WebKit still knows each name, M9): the older `enable-dns-prefetching` and `enable-hyperlink-auditing` settings do nothing since WebKitGTK 2.52 (the first stays off; the second, which warns at every view, isn't set since 2026-10-19), and `<a ping>` is otherwise sent, so the pings filter (3) blocks it. WebKitGTK 2.54 dropped `LinkDNSPrefetch` (WebKit 310198@main): `<link rel=dns-prefetch>` always runs there, so after Show images only the pings filter (3) keeps it from looking up a message's names; the unit test expects the name up to 2.52 and not from 2.54. Page cache, local storage, databases, WebGL, WebAudio, media and (in release builds) developer extras are off.
6. `cid:` parts come from a per-view URI scheme backed by the local blob store; a part belonging to another message never loads. Answers come from the main loop, never inside WebKit's call, and only for the load that asked: a view released, blanked or loaded again gets its request ended unanswered. A large message's inline parts come from the server by their section (`FetchPart`) and are served as the type the stored message declares (M5, ML-060); once downloaded they stay in the process's memory for the session (at most 32 MiB, none over 8 MiB, the least recently used dropped first, a message's parts dropped when it leaves the store), never on disk, and a reply copies them from there into its draft (2026-10-19).
7. View heights are capped at 16,000 px, and growth driven by viewport units is frozen (a hostile `150vh` would otherwise inflate the view).
8. WebKitGTK 6's web-process sandbox (bubblewrap) stays on: WebKitGTK 6's API has no switch to turn it off and Sealwax sets nothing that would. WebKit turns it off when `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS` is in the environment (tried with WebKitGTK 2.52.6: the web process then ran as Sealwax's own child, in Sealwax's namespaces), so `main` removes it first thing, in every build, while the process has one thread, and logs a warning without its value (M9). The self-tests run with it set, and `assert-web-sandbox` checks that the reader's and the composer's web processes run under bubblewrap in a PID namespace of their own. Only web processes run inside it; WebKit's network process is a plain child of the app.
9. **Show images** lifts the content filter for that message, in that reader, until Sealwax quits; nothing is stored. **Always for this sender** puts the sender's address (lower case) on a list in the store (schema v8); a message whose From address is on it loads its images with the filter off, under the same CSP, the same cookieless session and the same pings filter. A forged From address borrows that permission: the images tell the forger that the message was opened and from where, which is what remote images always tell; nothing else loads. Hide, or the toggle turned off, forgets the sender. In a conversation each message has its own banner, and a view that comes back for a body far off screen gets the filter again unless that message or its sender is allowed (M5, ML-058). The CSP still admits only https images, upgrading http ones. Every other load, in any pooled view, keeps the filter: a released view gets it back before it loads anything else (M1).
10. Views refuse new windows, script dialogs, permission requests, file and colour choosers, fullscreen, page-initiated printing, notifications and HTTP authentication. The context menu keeps Copy, Copy Link, Copy Image and Select All, plus Inspect Element in debug builds. Console messages never reach stdout (M1).
11. If a web process ends, the message is rendered once more; after a second crash it is shown as text (M1).

Isolated-world helper scripts are **not** bound by the page's CSP for `fetch()`: in S7 a helper `fetch()` reached a local test server with the CSP alone, and only the content filter stopped it. A reader view whose images the user allowed runs its helpers without the filter, so the reader's helpers load nothing at all (no fetch, request, image, source or URL; a unit test holds it since M9), and the composer's one `fetch()` reads only its own `blob:` URLs under a filter that is always on. With script markup off, no markup script or event handler ran even without the CSP (S2, S7).

### Composer

The composer view uses the same layers as the reader, without `https:` for images, in a web context and process of its own: script markup off, the CSP at construction (`img-src data: cid:`), a content filter that blocks everything but `cid:`, `data:`, `about:` and `blob:`, an ephemeral session, every navigation and new window refused, `hardware-acceleration-policy` NEVER. Paste and drop go through the allowlist cleaner; links are limited to http(s) and mailto; pasted or dropped images become `cid:` parts stored in the blob store and served only to the composer view that holds them (M6: a hostile paste with S7's cases made 0 requests to a local canary).

HTML that enters a draft from elsewhere (a quoted or forwarded original, a draft read back from the Drafts folder) goes through the same allowlist in Rust (`domain::compose::clean`: an html5ever pre-pass, then ammonia), keeping `https:`, `cid:` and typed base64 `data:` images; the composer's CSP still never loads remote images. The pre-pass reads tags as a tokenizer and ammonia builds a tree, so markup such as `<svg><p>` reads differently to the two; when the output shows a `cid:` image the caller doesn't hold, it goes through both once more, and its images are counted from the output's tags (M9, found by fuzzing). Replies, forwards and drafts read back are planned on worker threads. A reply or forward to an original with more than 256 KiB of HTML quotes its text (its plain part, else the text of its HTML's first 256 KiB) instead of its cleaned HTML, without its inline images; a forward carries them as attachments (M9: html5ever's tree builder is quadratic in the nesting depth). The pre-pass also leaves out the start tags that would nest deeper than WebKit's 512 levels, keeping their content ([depth limit](#hardening-m9)). The quick reply is plain text in a text view: no HTML, nothing loads.

### Attachments

- Opened from a new private folder (0700) under `$XDG_RUNTIME_DIR/<app-id>/attachments` (the cache folder without a runtime folder), as a file created 0600 with a safe name, never executable, with the desktop's default application (`gtk::FileLauncher`); the folder is emptied when Sealwax next starts, and the runtime folder at logout.
- **Safe names** (`domain::attachment`): the last path component, without control or invisible characters, look-alike dots made real, no leading dot, dash or space, no trailing dot or space, no `..`, at most 200 bytes, `attachment.<ext>` from the type when nothing is left; Download all never overwrites (`name (2).pdf`). The card shows that name, and the danger check below reads it as well as the name as sent: shortening a name whose last extension is too long to keep can leave another at its end (M9, found by fuzzing).
- **Never opened directly**, with a warning and Save only: programs, launchers, scripts, installers and packages by their last extension (case-insensitive, trailing dots and spaces ignored: `.desktop`, `.sh` and other shells, `.AppImage`, `.jar`, `.jnlp`, `.exe`, `.msi`, `.bat`, `.cmd`, `.com`, `.scr`, `.ps1`, `.vbs`, `.hta`, `.lnk`, `.run`, `.bin`, `.deb`, `.rpm`, `.apk`, `.snap`, `.flatpak` and `.flatpakref`, and the rest in the code) or MIME type; names that hide their type (direction overrides, a look-alike dot before what reads as an extension); and files whose content GIO identifies as one of those types when they are opened.
- Saved files (Save, Download all, Save as .eml) go through the file chooser (the portal's where there is one) and are never made executable.

### Print and Show Original

- **Print** renders the message in a view from the reader's pool (every layer above; remote images only where the user allowed them), held by a window that is never shown; Sealwax's isolated world adds the header as text. Page-initiated printing stays refused.
- **Show Original** shows the raw source as text in a read-only view, never rendered. For a large message stored as its text parts, Show Original and Save as .eml fetch the message whole first (`FetchOriginal`); the copy rebuilt from its text parts is never shown or saved.

### Outgoing mail

- Message-ID is generated by Sealwax with the sender's domain; mail-builder's `gethostname` feature and lettre's `hostname` feature are off; `hello_name` is 127.0.0.1.
- The transmitted copy never carries a Bcc header; the Sent copy is the transmitted bytes plus one `Bcc:` field (S7).
- A message is sent at most once (M6, [ADR-015](DECISIONS.md#adr-015-amendment--the-outbox-as-built-m6-2026-10-06)): the store records the send, with its built bytes, before SMTP DATA in a transaction committed with a full sync; a send left in that state when Sealwax stopped, or whose connection was lost while its data went out, is "may have been sent" and goes again only when the user says so, with the same bytes and Message-ID.
- No User-Agent or X-Mailer field. The Message-ID is always on the From address's domain (the builder refuses another); a forward carries no In-Reply-To or References. Names and subjects lose control characters before they are written. Recipients' addresses appear in logs only as counts, and refused ones never.
- `mailto:` links keep only their safe fields; `attach` / `attachment` stay ignored, and nothing is sent without the user's Send.

### Privacy

- Microsoft sign-in: the address never goes into the sign-in URL (no `login_hint`); the sign-in URL, code, tokens and the username are never logged (ML-032).
- Autodetect: the full address goes only to the domain's own HTTPS autoconfig; ISPDB, MX and SRV lookups use the domain. Plain-HTTP autoconfig is never used. A redirect that would carry the address to any other host is refused, however deeply percent-encoded (M9: two rounds were decoded before): S4b found `autoconfig.msn.com` redirecting to `www.msn.com` with the address kept, which S4's audit had missed. No request carries a Referer (M9: reqwest's default sent the first URL, address and all, to the host of any redirect it followed). Hosts that resolve to non-public addresses are neither fetched nor probed; since M9 that includes IPv6's 6to4 addresses of private ones, Teredo, IPv4-compatible, site-local and discard-only addresses. Server hosts a clientConfig document names are checked by name (no IP literal, no `localhost`); their addresses aren't checked before the login check connects, which only certificate verification guards.
- No avatars, favicons, BIMI or Gravatar lookups; no read receipts; no telemetry.
- Check for Updates (ADR-021 amendment, 2026-10-20) runs only when the user chooses it: one HTTPS GET of `api.github.com/repos/PixDevsApps/sealwax/releases/latest` with the User-Agent `Sealwax`, no cookie, no Referer, no proxy, the platform verifier, 20 s at most and an answer of 512 KiB at most. Only `tag_name` is read, and only as `vX.Y.Z` with plain numbers: the command the dialog offers to paste into a terminal is built from those numbers, never from the answer's text. Sealwax runs nothing itself.
- New-mail notifications (M7) give the desktop's notification server the sender and the subject, the user's choice at M7's start; the text is mail content, so control and direction characters are dropped (since M9 also the Arabic letter mark), it is capped (80 and 200 characters; since M9 also a count's list of senders), and the body is markup-escaped where the server reads markup. omarchy-shell writes toasts under `~/.local/state/omarchy/notifications/`; `[notifications] show = "count"` sends only a count, and `enabled = false` nothing.
- Development and spikes never put the user's address or personal data in network requests ([ADR-018](DECISIONS.md#adr-018--logging-and-privacy-2026-10-04)).

### Logging

Logs never contain message bodies, subjects, addresses, folder names, search text, tokens or protocol traces; AUTH lines are always redacted. Logs use account ids and counts. The search query's types (`Query`, `Term`, the store's FTS expression) and anything holding a notification's text print counts or lengths in `Debug` (M7).

A panic in a dependency's or the standard library's code is reported on stderr by thread and place, without its message, which may quote what was being parsed (imap-proto's names a character of the server's reply); Sealwax's own panics keep Rust's report (`infrastructure::logging::redact_dependency_panics`, M9). An account's sync that panics is logged with the account's id and the count in a row.

Third-party protocol crates are capped at `warn` whatever `RUST_LOG` says: S1 found that async-imap's trace logging prints the LOGIN password ([ADR-018 amendment](DECISIONS.md#adr-018-amendment--third-party-trace-logs-2026-10-04)). As built (`infrastructure::logging`, checked in M9): `async_imap`, `imap_proto`, `lettre`, `rustls`, `tokio_rustls`, `hickory`, `reqwest`, `hyper`, `hyper_util`, `h2`, `zbus`, `html5ever`, `markup5ever`, `html2text` and `mail_builder`, matched as prefixes; `log`-crate records go through the same caps. The other crates Sealwax links don't log. GLib, GTK and WebKit write to stderr through `g_log`, outside these caps. A test runs the testbed suites at trace level and greps the captured logs for credentials, tokens, addresses and folder names.

### Local data

- Private folders are created 0700 and files 0600 (database with its `-wal` and `-shm`, blobs, drafts, `accounts.toml` and its journal, temporary attachment copies under `$XDG_RUNTIME_DIR/<app-id>/attachments`; since M9 also `config.toml`, `keys.toml` and `accounts.toml` when the palette or Preferences creates them).
- The app never edits `~/.config` outside its own folder, `~/.local/state/omarchy` or system files, except through opt-in commands the user confirms: the default mail handler (Make Sealwax the Default Mail App…, which asks first; M6) and Start Sealwax at Login (M7), which asks before it writes `$XDG_CONFIG_HOME/autostart/<app-id>.desktop` and, turned off, deletes only that file.
- A POP3 account's mail lives only in the store and the blob store once the server deletes it (M8): the reader, attachments and Show Original take it from there, never from a server again, and the disk cap never evicts it, also when an IMAP account's cached body is the very same file (blobs are named by their content; M9 found the eviction taking it).
- Drafts, their parts and the outbox's built messages live in the store and the blob store (0600); a part's bytes stay until the draft is discarded or sent, even after the part is removed in the editor, and the disk cap never evicts them (M6).

## Mail rules (M9)

Mail rules are Sieve (RFC 5228) run by Sealwax on the mail it syncs ([ADR-020](DECISIONS.md#adr-020--folders-and-rules-sieve-run-by-sealwax-2026-10-09), `domain::sieve`). The script is the user's own file, but it may be pasted from anywhere, so the language is held to a subset:

- **Nothing leaves the machine and nothing is deleted for good:** `redirect`, `reject`, `vacation`, `notify` and every other command or extension outside the subset are refused by name when the script is checked, and a script that doesn't check runs nothing. `discard` moves the message to Trash; `addflag` and `setflag` refuse `\Deleted`; flags must be IMAP keywords, so nothing in a flag can break an IMAP command.
- **Limits:** a script is at most 1 MiB (`MAX_SCRIPT_BYTES`) and nests blocks, and tests inside tests, at most 32 levels deep (`MAX_NESTING`), both parse errors with their line and column. There are no loops or variables: a run executes each command at most once and evaluates each test at most once per message, and `:matches` takes at most value × pattern steps (no backtracking blow-up).
- **Privacy:** an error message names commands, tags and extensions, never a string from the script; the `Debug` of every type that holds script text (scripts, rule sets, rules, outcomes, errors) prints counts and kinds only, so rule text, addresses and folder names never reach a log.
- **Reading back:** the Rules dialog's model recognises a rule only when writing it again gives the same commands; anything else is kept as hand-written text, so saving from the dialog never changes what the rest of a script does (checked by the fuzz target on every input).
- **Running (B1):** a rule's actions are the user's own kinds of change, through the op queue: moves, copies and flags of the account's own folders, Trash for `discard`, never an expunge or anything sent. A header a rule needs is fetched with `BODY.PEEK[HEADER]` (nothing marked read) on the account's own connection. The engine logs counts, folder ids and an error's kind, never a header, an address, a subject, a folder name or the script.

## Review and fuzzing (M9)

ML-093 checked every rule above against the code as built through M8, with where it is enforced and which test holds it, and fixed what was small and safe.

- **Fuzzing:** coverage-guided libFuzzer on the stable toolchain (`fuzz/`, `tools/fuzz.sh`, [BUILD.md](BUILD.md#fuzzing-and-the-advisory-check-m9)), 12 targets (a 13th, Sieve rules, came with the rules in M9): raw messages through ingest, the reader, replies, forwards and the MIME builder; HTML through the reader's scan, the text conversion and the composer's cleaner, whose output must hold only allowlisted tags, attributes and URL schemes; plain text (format=flowed, quotes, snippets, links); link targets and texts; attachment names; autoconfig XML and redirects; the search query; `mailto:` links and recipients; `config.toml`, `keys.toml` and `accounts.toml` with the assistant's edits; theme colours; POP3's replies and line layer (which must never hand bytes read past a line to TLS); IMAP's folder names, roles and UID sets. Each target checks what its parser promises, and every crash found is a regression input in `fuzz/corpus/`, which `cargo test` runs. About 3.8 core-hours on 2026-10-07 found six faults in Sealwax's code, all fixed, a panic in imap-proto ([known limitations](#known-limitations)) and a debug assertion in mail-parser (debug builds only; `message::parse` catches it); the last runs found nothing.
- **Dependencies:** `Cargo.lock` matched against the public RustSec advisory database (`tools/advisories.py`): no vulnerability; one withdrawn notice (`ring` unmaintained, RUSTSEC-2025-0007).
- **Patched lettre** (2026-10-13): lettre 0.11.23 is vendored in `vendor/lettre/` with one change, a reply line of up to 16 KiB instead of 1,000 bytes ([issue #2](https://github.com/PixDevsApps/sealwax/issues/2)); the 100,000-byte cap on a whole reply, which bounds what a server can make Sealwax hold, is unchanged. The advisory check covers it ([vendor/README.md](../vendor/README.md)).

## Hardening (M9)

Three of the review's proposals, chosen by the user on 2026-10-07 and built on `m9-hardening`:

- **HTML parse limit (F14):** html5ever's tree builder takes time quadratic in the nesting depth, so outside the reader Sealwax parses at most 256 KiB of a message's HTML into a tree (`message::HTML_PARSE_LIMIT`, 1 MiB before): `message::html_to_text` (the search text and the snippet at sync, a reply's text, the reader's check for PGP armour in HTML and its text fallback) reads the first 256 KiB, and a reply or forward to an original with more quotes its text ([Composer](#composer)). Mail under the limit is handled as before. Measured in release on one machine: a message of 990,000 bytes of nested lists took 19.8 s at sync before and 7.4 s now, and one of 990,000 bytes of open `<ul>` 175 s before and 6.3 s now. The reader renders HTML in WebKit, not html5ever; its scan for colours and remote images (`domain::html_scan`) reads the whole HTML without a tree.
- **An account's sync started again after a panic (F15):** an account's actor, IMAP or POP3, that ends in a panic instead of a stop (imap-proto's, on a reply from the server) is started again after the backoff a second failed connection waits (1 s, doubling with each panic in a row to 5 minutes, jittered; a run longer than 5 minutes starts the count over), and the account shows offline meanwhile. An actor stopped on purpose (removal, quit, `accounts.toml` changed) stays stopped, also when the stop comes during the wait; `Reconnect` starts it at once. The log names the account's id and the count, never the panic's message. An IDLE connection that panics is started again at the next account pass, as before, now with a log line, and goes with its actor.
- **WebKit's sandbox stays on:** [layer 8](#message-rendering).

Then the hardening's own findings N1 and N2, on `m9-depth`:

- **Depth limit (N1, N2):** html2text drops a render tree it didn't finish recursively (a text part too narrow for 40-odd nested lists), so 14,563 nested lists overflowed a 2 MiB thread's stack, which ends the process; html2text and html5ever's tree builder also take time quadratic in the depth. `domain::html_depth` counts, in one pass with html5ever's tokenizer, the stack of open elements the tree builder would keep (implied end tags, scopes, a table's implied rows, formatting elements opened again). HTML nested deeper than WebKit's 512 levels takes its search text, snippet and sent text part from mail-parser's one-pass converter, and the cleaner (quotes, drafts read back) leaves out the deeper start tags and keeps their content. Whatever the count misses, html2text only ever renders a tree flattened below 1,024 levels; dropping one that deep took at most 224 KB of stack in release and 363 KB in debug. Mail within the limit takes the same path as before (no difference in 20,061 inputs compared). Measured in release on one machine: 87,381 nested `<s>` 36.5 s at sync before, 0.9 ms now; 65,534 open `<ul>` 7.3 s and 23 s to plan a reply before, 1.0 ms and 9.2 ms now.
- **A build that ends the process isn't run again by itself:** the store records that a send's message, or a draft's Drafts-folder copy, is being built until the build returns (schema v12). A start that finds a send so gives it back to its draft as failed ("Sealwax stopped while preparing it"; never sent, ADR-015's at-most-once rules unchanged), and a copy so waits for the draft to change. A message whose build crashes Sealwax would otherwise be built again, and crash it again, at every start.

## Known limitations

- **Plaintext keyring on this machine:** gnome-keyring's "Default keyring" is passwordless, so its file is stored unencrypted and protected only by full-disk encryption. Sealwax can't fix this; the [user guide](USER_GUIDE.md#giving-your-keyring-a-password) explains how to give the keyring a password.
- **The depth count is close, not exact:** on random tag soup it was at most four levels short of html5ever's tree, and a few crafted soups gain about two levels per repetition on it. The ones found still exceed the limit when repeated to 256 KiB (at most 80 ms to clean them; release, one machine), HTML just under the limit repeated to 256 KiB took at most 0.19 s, and the flattening below 1,024 levels keeps html2text's stack bounded whatever the count says. Not every shape was measured. The reader's scan of nested CSS braces is still quadratic (N3).
- **A hostile IMAP server can keep an account failing:** imap-proto 0.17.0 panics on a reply whose response code is followed at once by a non-ASCII character. Since M9 the account's sync starts again after the backoff and shows offline meanwhile, but a server that sends such a reply on every pass keeps it failing. Only the server itself can send it (TLS); it is reported upstream as djc/imap-proto#210.
- **WebKit's sandbox can't be turned off:** it needs bubblewrap and unprivileged user namespaces; where a container lacks them, web processes may fail to start (not tried; ML-095's clean-container test).
- **Self-signed servers elsewhere** (some self-hosted servers) can't be added: only a server on this computer, such as Proton Mail Bridge, can be trusted with its own certificate. A program on this computer that listens on the same port first, before Bridge starts, would be offered for trust in the assistant like Bridge; the fingerprint is shown so it can be compared.
- **Encrypted and signed mail** (PGP, S/MIME) is displayed gracefully but not decrypted or verified in 1.0: encrypted mail shows a notice in place of its body (the ciphertext is never shown, and the encrypted part can be saved); signed mail shows its content with "Signed · not checked"; signature parts stay out of the attachment cards (M5, ML-064).
