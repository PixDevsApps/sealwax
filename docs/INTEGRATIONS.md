# Integrations

Synced: 2026-10-05

How Sealwax fits Omarchy 4, Hyprland and the mail providers. Facts about this machine were read on 2026-10-04 (Omarchy 4.0.4, Hyprland 0.56.2); anything marked *to verify* is checked in the named spike before code depends on it.

## Omarchy theme

- **Active palette:** `~/.local/state/omarchy/current/theme/colors.toml`, a flat `key = "#rrggbb"` file with a `mode` key (`dark` or `light`). Omarchy hardcodes `$HOME/.local/state` and ignores `XDG_STATE_HOME`. `~/.config/omarchy/current` no longer exists in Omarchy 4.
- **Resolver:** `/usr/share/omarchy/bin/omarchy-theme-color --file <colors.toml> --all` prints `key<TAB>value` lines with every alias and fallback applied (`bg`, `color0`–`color15`, `purple`, derived `dark_background` and so on). Stet's Rust port of the cascade is the fallback when the script is missing.
- **Light or dark:** first match wins: `mode`, legacy `theme_type`, a `light.mode` file, then background luminance (R+G+B > 382 is light). Five stock themes are light: catppuccin-latte, flexoki-light, white, rose-pine, lupine.
- **What changes on a switch** (`omarchy-theme-set`): `current/next-theme/` is staged, then `rm -rf current/theme; mv current/next-theme current/theme`, then `theme.name` is rewritten. The reload trigger (from Stet) watches `current/` and its parent: `theme.name` ChangesDoneHint, or `theme` Renamed; debounce 150 ms; retry if a read hits the gap while `theme/` is replaced. Never watch files inside `theme/`; they are replaced.
- **gsettings lag behind:** `omarchy-theme-set-gnome` sets `color-scheme` and `gtk-theme` after the swap, so Sealwax takes `mode` from `colors.toml` and forces `adw::StyleManager`.
- **No hook needed:** the directory watch sees every switch. `~/.config/omarchy/hooks/theme-set.d/` exists, but writing there would edit the user's config.
- **Theme-provided CSS (P2):** if a theme ships `<app>.css`, Omarchy copies it to `current/theme/`; Sealwax loads it after its generated CSS, giving theme authors an override point without a template.

## Fonts

- `omarchy font set` writes `~/.config/fontconfig/fonts.conf`, putting the font first for `monospace`; `fc-match monospace -f '%{family[0]}'` returns it (JetBrainsMono Nerd Font here). Sealwax watches `~/.config/fontconfig/` as Stet does.
- `/etc/fonts/conf.d/50-omarchy.conf` maps sans-serif to Liberation Sans. WebKit's default fonts are set explicitly from these families.
- `omarchy display text size` writes `[font] base-size` to `~/.config/omarchy/shell.toml` (12 px default). omarchy-shell merges this user file over the theme's generated `current/theme/shell.toml` (which carries `[controls]` and `[spacing]`); Sealwax reads both the same way, and its chrome scale follows the result.
- gsettings `font-name` is not updated by Omarchy and is not read.

## Hyprland

- Configured in Lua (`~/.config/hypr/hyprland.lua` loads Omarchy's defaults, then the user's modules); `hyprctl reload` applies, `hyprctl configerrors` checks.
- **Corner radius:** `hyprctl -j getoption decoration:rounding` (8 here, 0 on stock Omarchy), read at start and after theme changes, as omarchy-shell does ([ADR-019](DECISIONS.md#adr-019--corner-radius-follows-hyprland-2026-10-04)).
- **Window class:** GTK4 apps use the app-id as their Wayland app_id, so rules match `^io\.github\.pixdevsapps\.Sealwax$`.
- **Focus and scale (S6):** Omarchy sets `misc.focus_on_activate = true`, so `present()` focuses the window (2–4 ms). `GDK_SCALE=2` in the session environment has no effect on GTK 4 Wayland apps; it still applies to X11 and XWayland programs.
- **No title bar:** Sealwax shows no title bar and no window controls when `HYPRLAND_INSTANCE_SIGNATURE` is set or `XDG_CURRENT_DESKTOP` contains `Hyprland`; elsewhere the pane bars carry the window controls at the window's edges and drag the window (M1).
- **Default opacity:** Omarchy tags every window `default-opacity` (0.985 / 0.96); an opt-out snippet is `o.window(<match>, { tag = "-default-opacity" })`. This machine's `looknfeel.lua` already forces windows opaque.
- **Key binding:** the user's `~/.config/hypr/bindings.lua` binds SUPER+SHIFT+E to BlueMail. The snippet the user can paste once Sealwax is installed (ML-085):
  ```lua
  hl.unbind("SUPER + SHIFT + E")
  o.bind("SUPER + SHIFT + E", "Sealwax", { launch = "sealwax", focus = "^io\\.github\\.pixdevsapps\\.Sealwax$" })
  ```
  Sealwax never edits Hyprland files itself.

## omarchy-shell (notifications, launcher)

- omarchy-shell (Quickshell 0.3.1) owns `org.freedesktop.Notifications`. Measured in S6: name and vendor `quickshell`, spec 1.2, capabilities `persistence`, `body`, `body-markup`, `body-hyperlinks`, `actions`, `icon-static`; a notification is accepted in 0.8 ms.
- **Click behaviour** (read in `/usr/share/omarchy/shell/plugins/notifications/Service.qml`): the shell invokes the notification's `default` action if there is one; otherwise it focuses a window whose class matches `app_name` as a case-insensitive regex. Sealwax always sends a `default` action. **Cards show no action buttons:** a left click runs `default`, a right click dismisses. GLib 2.88 ignores the `ActivationToken` signal; GTK's `present()` requests its own token and Omarchy's `focus_on_activate = true` focuses the window (2–4 ms, S6). A real click is the user's manual check.
- Low-urgency notifications stay ≥ 5 s, normal ≥ 8 s, none longer than 30 s; Do Not Disturb stores them silently.
- **History:** toasts are mirrored under `~/.local/state/omarchy/notifications/` and moved to `history/` (newest 10) when they leave the screen. Restored and history entries have no live actions, so a click reaches the app only while it runs (background mode, D6).
- **What GLib sends** (S6): `app_name` is the process name, so the app sets it to the product name (`g_set_prgname`) before its first notification; the app-id goes in the `desktop-entry` hint, the themed icon name in `image-path`, and actions as detailed action names.
- **Launcher:** the `.desktop` file is found through Quickshell `DesktopEntries` and started with `uwsm-app -- gtk-launch <id>.desktop`.
- **Omarchy menu (snippet only):** entries can be added in `~/.config/omarchy/extensions/omarchy-menu.jsonc` (ids like `"mail.compose"`). Documented in M7, never written by the app.
- **Unread count in the bar:** a 1.x bar-widget plugin (manifest `kinds: ["bar-widget"]`, QML with `qs.Commons`), following the user's Hertz Radio and Scarlett Control plugins.

## Secret Service

- gnome-keyring 50 owns `org.freedesktop.secrets` on this machine; the "Default keyring" is unlocked and passwordless, so its file is stored unencrypted (protected by full-disk encryption only). See [SECURITY.md](SECURITY.md#known-limitations).
- Sealwax stores items through oo7 with attributes `{ app: <app-id>, account: <uuid>, kind: password | refresh-token }`. Headless runs use the in-memory store (the private bus starts no services).

## Default mail handler

- Current handler: `bluemail.desktop`. `~/.config/mimeapps.list` still names a removed Thunderbird for `message/rfc822`; Sealwax does not touch it.
- Sealwax's desktop file declares `MimeType=x-scheme-handler/mailto;`. "Make Sealwax the default email app" is an opt-in command that asks first and then runs `xdg-mime default <app-id>.desktop x-scheme-handler/mailto` (Stet's `set_default` pattern).
- `mailto:` URIs are parsed per RFC 6068; `attach` / `attachment` parameters are ignored. Only `to`, `cc`, `bcc`, `subject`, `body` and `in-reply-to` are kept, and control characters are stripped from header values (S6).
- **Forwarding (S6):** a second process forwards a `mailto:` to the running instance in ~51 ms, 49 of them loading libraries; a D-Bus `org.freedesktop.Application.Open` call, which launchers use for a `DBusActivatable` app, takes 0.5 ms. The desktop file keeps `DBusActivatable=true`, and the app handles both `open` and `command-line` (built in M1). With no instance running, a command line first asks the bus to start the installed service (Stet's pattern), so `xdg-open mailto:…` from a browser starts a Sealwax that doesn't belong to the browser; verified headlessly with a private bus, `xdg-open` on the live desktop not yet.

## Network and sleep

- GIO's network monitor uses NetworkManager here (`GNetworkMonitorNM`); logind's `PrepareForSleep` signal is on the system bus (read-only subscription).
- IMAP IDLE never notices a silently dead connection: in S6 one went unnoticed for 10 s, and it would stay unnoticed until the IDLE restart plus the read timeout. On `PrepareForSleep(false)` and when the network monitor reports the network back, the engine drops and reconnects every connection at once ([ADR-003](DECISIONS.md#adr-003-amendment--desktop-integration-measured-in-s6-2026-10-04)); the reconnect itself took ~14 ms on localhost.
- Real suspend, Wi-Fi reassociation and NAT timeouts are not verified yet: the user's manual check first, then the M3 soak.


## Account autodiscovery sources

Measured in S4 and S4b on 2026-10-04 ([S4](spikes/S4-autodetect.md), [S4b](spikes/S4b-autodetect.md)) and built in M2 (ML-030, [m2/autoconfig.md](m2/autoconfig.md)): the pure half in `domain/src/autoconfig/`, the lookups in `engine/src/autoconfig/`. The user declined presets for Norwegian providers; S4b's general rules (R1–R3 below) stand in for them. The accuracy bar counts the second login attempt (user decision 2026-10-04): 45/50 on S4's list. The sources run in parallel inside one future; dropping it cancels every lookup. For each protocol, the highest-ranked source that answers wins once every higher-ranked source has answered, failed or timed out; implicit TLS beats STARTTLS within a source (RFC 8314). Only the settled answer is used; at the 10 s cap the best answer so far is taken.

1. Built-in presets for global providers (offline, no request), including MX host suffixes for hosted platforms: Google, Microsoft 365 (`*.mail.protection.outlook.com`, `*.mx.microsoft`), Outlook.com (`*.olc.protection.outlook.com`), Fastmail (`messagingengine.com`), Zoho by region, iCloud custom domains (`*.mail.icloud.com`, username asked); Proton and Tuta as "not supported". No presets for Norwegian providers (declined 2026-10-04).
2. The domain's own autoconfig over HTTPS (4 s): `https://autoconfig.<domain>/mail/config-v1.1.xml?emailaddress=<address>`. The only place the full address is sent. Redirects are followed only over HTTPS, at most three, to the same host or inside the domain, and a redirect that would carry the address to any other host is refused (S4b found `autoconfig.msn.com` redirecting to `www.msn.com` with the address kept).
3. The Mozilla ISPDB: `https://autoconfig.thunderbird.net/v1.1/<domain>` (domain only). **M2:** above SRV records; judged alone it was right for 18 of 20 answers on S4's list and 8 of 8 on S4b's held-out list, SRV for 8 of 11 and 2 of 4.
4. DNS SRV records (RFC 6186, RFC 8314). **M2:** the best record per protocol (implicit TLS first, then priority and weight) must pass the TLS check before it is offered; if it fails, the next one is tried (two at most). `_submission` on 465 and `_imap` on 993 are read as implicit TLS (S4b met an `_submission` record on 465 whose literal reading fails). R2 (S4b): when a target's first label is not `imap`/`smtp`, and the conventional name in the same parent domain resolves to the same addresses and passes the same TLS check on the same port, the conventional name is used.
5. The user's own domain (S4b, R1): if `imap.<domain>` answers IMAP on 993 with a certificate valid for that name, it — with `smtp.<domain>` on 465 or 587 — outranks everything inferred from the MX records. A null MX, or an MX of a provider that is "not supported", still ends the search.
6. MX → the preset suffix table. A null MX means the domain has no mail. **M2:** when no preset matches, an `autodiscover.<domain>` CNAME to `autodiscover.outlook.com` (Exchange Online's DNS setup) means Microsoft 365 behind the organization's own MX gateway.
7. `https://<domain>/.well-known/autoconfig/mail/config-v1.1.xml`, capped at 1.5 s (slow and rarely useful in S4).
8. The MX operator (S4b, R3; the registrable domain of up to two MX hosts, public suffix list): its own autoconfig requested without any address (1.5 s), then the ISPDB.
9. Guarded probing, TLS only, stopping when the preferred host answers; it starts when the other sources are done or after 2 s, and waits for the MX answer. First the user's domain (`imap.`, `mail.` and the bare name on 993 and 143 with STARTTLS; `smtp.`, `mail.` and the bare name on 465 and 587 with STARTTLS), then the MX operator's `imap.`/`mail.` and `smtp.`/`mail.`, accepted only when the operator offers both IMAP and submission (an IMAP-only answer offered a domain marketplace's server for a domain without mail in S4b).

Time limits (S4's): HTTP 4 s per request; DNS 2 s, two attempts; 4.5 s per source; 3 s per TLS check; probes within 5 s; the whole search 10 s. A TLS check sends only CAPABILITY, STARTTLS and `EHLO [127.0.0.1]`, and each endpoint is checked at most once per search.

Hosts from network sources that are loopback, private or IP literals are never used (Proton's own autoconfig returns the Bridge on 127.0.0.1; Proton is recognized by its preset), and hosts that resolve to non-public addresses are neither fetched nor probed (S4b). Results are shown for confirmation before the password is sent (`DetectedSettings::confirm`) when they came only from the MX operator's hosts (user decision 2026-10-04: with the username field), or when an SRV or MX-derived host lies outside the user's domain and no preset names it. Microsoft's hosts (`*.outlook.com`, `*.office365.com`) are always OAuth. One resolver (hickory) with fully qualified names serves HTTP, DNS and probes, so a search domain such as `home` never turns `autoconfig.<domain>` into `autoconfig.<domain>.home`. HTTP proxies from the environment are not used, so the non-public check always applies.

IMAP login and SMTP AUTH are verified before anything is saved, with **at most 2 attempts**: the engine holds a budget of 2 and spends one before any authentication command; the first attempt uses the top-ranked IMAP host and the detected username form (`DetectedSettings::username`, one form for both protocols); the second comes only after an authentication failure and uses the other form (`second_username`: full address ↔ local part, as RFC 6186 recommends); the password never goes to a lower-ranked host; SMTP reuses the form that worked; where a preset says the username can't be derived (iCloud custom domains) the user is asked first. iCloud's preset starts with the full address, which Apple documents for SMTP and as the IMAP fallback. S4b measured that part of the accuracy rests on the second attempt: Telenor's documented local-part username is reached only by it. No network evidence marks a provider-generated account name such as Domeneshop's, so for those results the confirmation screen shows the username field (user decision 2026-10-04).
